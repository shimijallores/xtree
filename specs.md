# XTree — Spec

**XTree: a UML-driven code comprehension engine for Vibe Coders**

XTree turns your codebase into live, UML-based diagrams and explains every node with an LLM running entirely on your own GPU, so your code never leaves your machine.

Built for the AppBuildersPH Hackathon 2026 (Local AI track). Code freeze: 10:00 AM, Oct 10.

---

## 1. Problem

Vibe coders (developers working with AI coding agents) receive large volumes of generated code they did not write. Reading it file by file is slow and overwhelming, and it's hard to see how functions, classes and types connect. Existing UML tools draw static diagrams but don't explain anything. Cloud AI explainers send proprietary code to third parties and charge per request, which makes continuous re-analysis on every save impractical.

**Target user:** a developer who opens an unfamiliar or AI-modified file (e.g. `AddToCart.js`) and wants to understand its flow in minutes.

## 2. Why local AI

| Concern | Cloud API | XTree (local) |
|---|---|---|
| Privacy | Source code sent to a third party | Code never leaves the machine |
| Cost | Pay per token, on every save | Free after model download |
| Latency for re-analysis | Network round trip per card | GPU-local, cached per function |
| Offline | Breaks | Fully works with Wi-Fi off |

Re-explaining code on every file save is only viable when inference is local and free.

## 3. Core principle: the parser draws, the LLM explains

- **Static analysis is the source of truth for structure.** Nodes, edges, types and call relationships come from a parser and are deterministic. The LLM never invents graph edges.
- **The local LLM provides meaning.** Card summaries, the flow walkthrough and chat answers are generated by the LLM, always grounded in parser facts plus real source code.

## 4. Scope

### In scope
- JavaScript and TypeScript (`.js`, `.jsx`, `.ts`, `.tsx`)
- Localhost web app launched with one command
- Ollama as the inference runtime

### Out of scope (hackathon)
- Other languages
- VS Code extension packaging (roadmap)
- Editing code from XTree (read-only)
- Cloud LLM fallback

## 5. Features

Priority: **P0** = must-have, **P1** = should-have, **P2** = cut first.

### F1. Project load and entry selection (P0)
- `npx xtree ./path/to/project` (or `npm start -- ./path`) starts the server and opens `http://localhost:5173`.
- The left sidebar shows a file tree of supported files. Clicking a file sets it as the **entry file**.
- Ignores `node_modules`, `dist`, `build`, `.git`, and anything matched by `.gitignore`.

### F2. Static analysis graph (P0)
From the entry file, follow relative imports up to **depth 2** (configurable later, P2).

Extracted symbols:
- functions (declarations, arrow functions assigned to consts, exported functions)
- classes, with constructor, fields, methods and visibility (`public` / `private` / `protected`, `#private`)
- interfaces, type aliases, enums

Extracted edges:
| Edge | Meaning | Source |
|---|---|---|
| `calls` | function/method A calls B | call expressions resolved to known symbols |
| `contains` | class contains method | class body |
| `uses-type` | function/class references a type | type annotations |
| `extends` / `implements` | inheritance | heritage clauses |
| `imports` | file-level dependency | import statements |

Calls to symbols that can't be resolved (library calls, dynamic dispatch) are omitted or shown as a faded "external" stub. They are never guessed.

**Parser:** TypeScript Compiler API (`typescript` package). It handles both JS and TS, resolves imports, and gives type info. tree-sitter is the fallback if performance is a problem.

### F3. UML canvas (P0)
Rendered with React Flow, with auto-layout via `elkjs` (layered, left to right, following the call flow).

Node types (UML conventions):
- **Function card:** title `ƒ name(params): ReturnType`, a collapsible syntax-highlighted source body, and the LLM summary line.
- **Class box:** UML three-compartment layout (name / fields / methods), with `+` public, `-` private, `#` protected markers. Methods are nested rows that can be expanded to show source.
- **Interface / type box:** header «interface» or «type», with a fields compartment. Type nodes cluster in their own lane.
- **External stub:** a faded pill for unresolved calls.

Edge styles:
- `calls`: solid arrow, numbered in call order inside the caller (1, 2, 3…), in sequence-diagram style
- `uses-type` / association: dashed arrow
- `extends`: hollow triangle head
- `implements`: dashed line with hollow triangle head

Interactions: pan, zoom, drag, minimap, a search box that jumps to a symbol, and clicking a node to select it.

### F4. Streamed card summaries (P0)
- After the graph renders (instantly), each node gets a one-line summary generated in the background.
- Summaries generate in a queue, entry file first, in breadth-first order. Tokens stream to the card over WebSocket.
- **Cache:** keyed by `sha256(symbol source + model name + prompt version)`, stored in `.xtree/cache.json` in the project. Unchanged code is never re-explained.

### F5. Live updates (P0)
- `chokidar` watches the project. On save, it re-parses the affected file(s) and diffs the symbol set.
- Changed symbols get a **"changed"** badge (with a highlight that fades after 10 seconds) and a regenerated summary. Cached cards stay as they are.
- Added or removed symbols animate in or out. The layout re-runs but keeps the positions of existing nodes stable.

### F6. Explain flow walkthrough (P1)
- An "Explain flow" button on the entry function, or on any selected function.
- The LLM receives the call subgraph (sources plus ordered edges) and returns a numbered step list.
- The right panel shows the steps. Clicking or stepping through highlights the matching node and edge on the canvas and pans to it.
- The output format is strict JSON: `[{ "step": 1, "symbolId": "...", "text": "..." }]`. Invalid `symbolId`s are dropped.

### F7. Grounded chat (P1)
- A right-side panel with a chat input.
- **Context:** pinned nodes (click the pin on a card) plus their direct neighbors. If nothing is pinned, the context is the entry file's flow. Context is capped at about 6k tokens, trimming the farthest neighbors first.
- The prompt includes parser facts: callers, callees and types for each node in context.
- Symbol names in answers that match graph symbols render as **clickable chips** that pan to and highlight the node.
- Read-only, session memory only.

### F8. Settings (P2)
- Model name, Ollama URL and traversal depth, set via `xtree.config.json` or env vars (`XTREE_MODEL`, `OLLAMA_HOST`). No settings UI unless time allows.

### F9. Status and offline indicator (P1)
- A top bar shows the model name, Ollama connection status, queue progress ("summaries 12/30") and a "Running 100% locally" badge.

## 7. Data model

```ts
type SymbolKind = "function" | "method" | "class" | "interface" | "type" | "enum" | "external";
type EdgeKind = "calls" | "contains" | "uses-type" | "extends" | "implements" | "imports";
type Visibility = "public" | "private" | "protected";

interface CodeSymbol {
  id: string;            // `${relPath}#${qualifiedName}`, e.g. "src/cart.ts#Inventory.reserve"
  kind: SymbolKind;
  name: string;
  file: string;          // relative path
  range: { start: number; end: number }; // line numbers
  signature: string;     // "reserve(productId: string, quantity: number): void"
  source: string;
  hash: string;          // sha256 of source
  parentId?: string;     // method -> class
  visibility?: Visibility;
  fields?: { name: string; type: string; visibility: Visibility }[]; // class/interface
  summary?: string;      // filled by LLM
  changed?: boolean;
}

interface CodeEdge {
  id: string;
  kind: EdgeKind;
  from: string;
  to: string;
  order?: number;        // call order within caller, for numbering
}

interface Graph {
  entry: string;         // entry file
  symbols: CodeSymbol[];
  edges: CodeEdge[];
}
```

## 8. API

REST:
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/files` | Supported file tree |
| POST | `/api/graph` | `{ entry, depth }` → `Graph` |
| POST | `/api/explain-flow` | `{ symbolId }` → streamed via WS, final JSON steps |
| POST | `/api/chat` | `{ message, pinned: string[], history }` → streamed via WS |
| GET | `/api/status` | Ollama reachable, model loaded, queue size |

WebSocket `/ws` server → client messages:
```ts
| { type: "summary.token"; symbolId: string; token: string }
| { type: "summary.done"; symbolId: string; summary: string }
| { type: "graph.diff"; added: CodeSymbol[]; removed: string[]; changed: CodeSymbol[]; edges: CodeEdge[] }
| { type: "flow.token" | "chat.token"; requestId: string; token: string }
| { type: "flow.done"; requestId: string; steps: FlowStep[] }
| { type: "chat.done"; requestId: string; text: string }
| { type: "status"; ollama: boolean; model: string; queued: number }
```

## 9. LLM prompts

Every prompt uses the system message: *"You explain code to a developer. Only describe what the given code does. If information is missing, say so. Never invent functions or calls."*

- **Summary:** input is the signature, source, callers and callees. Output is one sentence of at most 20 words, with no code. `temperature: 0.2`, `num_predict: 60`.
- **Flow:** input is ordered call subgraph sources. Output is the JSON steps (§F6), using Ollama `format: "json"`.
- **Chat:** input is the context block (pinned plus neighbors, with facts) and the history. Output is markdown that refers to symbols by exact name.

Ollama options: `keep_alive: "30m"`, `num_ctx: 8192`. The queue has concurrency 1, and chat/flow requests take priority over background summaries.

## 10. Model and hardware

Target machine: RTX 3050 8 GB VRAM, Intel i3 11th gen.

- Default: `qwen2.5-coder:7b` (Q4, ~4.7 GB VRAM).
- Fallback: `qwen2.5-coder:3b`, if 7b throughput is too low in testing.

## 11. Sample project: `examples/shop-app`

A small, deliberately interconnected TS project for the demo and for judges to reproduce:
- `AddToCart.ts`: entry, `addToCart()` → validates, prices, reserves stock
- `pricing.ts`: `calculateOrderTotal`, `applyDiscount`, `calculateTax`

It's about 200 lines and depth 2 from `AddToCart.ts`, and includes one class, one interface hierarchy (`implements`) and private members to show UML notation. It's disclosed as a demo asset written during the hackathon.

## 13. Error handling

- **Ollama down or model missing:** the canvas still works. Cards show "Local model unavailable", and the top bar shows setup instructions (`ollama pull qwen2.5-coder:7b`).
- **Parse errors:** the file shows a warning badge, and the last good graph for that file is kept.
- **LLM timeout (60 s):** the job is marked failed, with a retry button on the card.
- **Very large file or graph (> 150 nodes):** collapse method bodies by default and warn the user.

## 14. Acceptance criteria

1. `npm install && npm start -- examples/shop-app` opens the UI with no errors.
2. Selecting `AddToCart.ts` renders all symbols to depth 2 within 2 s, with correct `calls`, `contains`, `uses-type` and `implements` edges. Spot-check against the source.
3. Class nodes show UML compartments and visibility markers. Interfaces show «interface».
4. Summaries stream onto every card, and a reload serves them from cache instantly.
5. Editing `calculateOrderTotal` and saving updates only that card (badge plus new summary) within 5 s, plus model time.
6. "Explain flow" produces steps that highlight existing nodes only.
7. Chat answers about pinned cards include clickable symbol chips that pan the canvas.
8. With network disabled, items 2–7 still work.
9. Servers listen on `127.0.0.1` only.

## 15. Demo script (~1 min)

1. Run `npx xtree examples/shop-app` and click `AddToCart.ts`. The UML canvas appears instantly.
2. Summaries stream onto the cards from the local model.
3. Click "Explain flow". Steps highlight the path through pricing and inventory.
4. Ask the chat "What happens if stock runs out?" Answer chips jump to `Inventory.reserve`.
5. An AI agent edits `applyDiscount` in the editor. Only that card updates with a "changed" badge.
6. Turn Wi-Fi off and repeat step 4. It still works. Close on: "Your code never left this laptop."
